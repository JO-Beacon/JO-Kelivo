用 Dart 写一个快速排序，并解释分区逻辑。

JO-AIClient 
List<int> quickSort(List<int> a) {
  if (a.length <= 1) return a;
  final pivot = a[a.length ~/ 2];
  final lo = <int>[], eq = <int>[], hi = <int>[];
  for (final x in a) {
    if (x < pivot) lo.add(x);
    else if (x > pivot) hi.add(x);
    else eq.add(x);
  }
  return [...quickSort(lo), ...eq, ...quickSort(hi)];
}

分区逻辑：取中间元素为基准，把序列切成“小于 / 等于 / 大于”三段，等于段一次落位，只递归两侧。读起来最直观，代价是每一层都新建列表。

void quickSort(List<int> a, [int lo = 0, int hi = -1]) {
  hi = hi < 0 ? a.length - 1 : hi;
  if (lo >= hi) return;
  final pivot = a[hi];
  var i = lo;
  for (var j = lo; j < hi; j++) {
    if (a[j] < pivot) {
      final t = a[i]; a[i] = a[j]; a[j] = t; i++;
    }
  }
  final t = a[i]; a[i] = a[hi]; a[hi] = t;
  quickSort(a, lo, i - 1);
  quickSort(a, i + 1, hi);
}

分区逻辑（Lomuto）：以末尾元素为基准，i 左侧是已确认的“小于区”。扫描结束后把基准换到 i，此时基准已落在最终位置，左右两段各自递归。全程原地交换，没有额外列表分配。

先给结论：生产代码里更推荐直接 list.sort()。如果一定要自己实现，注意三点：

  • 基准选择：固定取末尾，在已排序输入上会退化成 O(n²)；取中位数或随机可规避。
  • 相等元素：三路分区让等于基准的元素一次落位，重复值多的数据收益明显。
  • 递归深度：先递归较短一侧、较长一侧改成循环，可把栈深度压到 O(log n)。

分区做的事始终一样：把序列重排为“小于基准 | 等于基准 | 大于基准”，基准段所在位置就是它的最终位置。

class CounterModel extends ChangeNotifier {
  int _value = 0;
  int get value => _value;

  void increment() {
    _value++;
    notifyListeners();
  }
}

思路：状态从 Widget 挪进 ChangeNotifier，Widget 只负责监听和渲染。测试直接实例化 Model 断言 value，不需要 WidgetTester。改造量最小，适合在现有代码上渐进迁移。

final counterProvider =
    NotifierProvider<CounterNotifier, int>(CounterNotifier.new);

class CounterNotifier extends Notifier<int> {
  @override
  int build() => 0;
  void increment() => state++;
}

思路：依赖关系由 provider 图声明，不再靠 context 层层传递，也不会在运行时才抛 ProviderNotFoundException。测试用 ProviderContainer 覆盖依赖，可以完全脱离 Widget 树验证业务逻辑。

sealed class CounterEvent {}
class Increment extends CounterEvent {}

class CounterBloc extends Bloc<CounterEvent, int> {
  CounterBloc() : super(0) {
    on<Increment>((_, emit) => emit(state + 1));
  }
}

思路：任何状态变更都必须经由事件，emit 序列可以用 blocTest 直接断言。约束最强、样板也最多，适合多人协作、需要追溯“状态是被哪个事件改的”的场景。

01

产品能力

按来源分成两组：JO-AIClient 在上游之上新增的能力，以及从 Kelivo 继承下来的基础能力。

独有JO-AIClient 独有功能

消息级上下文树

  • 消息分支创建、切换、重新生成、从历史消息继续对话
  • 按树结构精确删除：删单条、删后续、删当前分支、删分叉节点
  • 分支关系、分叉锚点、分支选择与活动分支历史完整存入 SQLite，聊天界面默认只显示当前活动分支
  • 上下文树完整性保护：持久化前做结构校验并生成稳定指纹，异常时保留原始数据并提供诊断入口，不静默修复

无损导入

  • Chatbox 全版本导入：1.22 以下走树形 JSON，1.22 起走 ZIP 备份，两条路都完整重建消息分支树，不把分叉对话线性化拍平成单链
  • DeepSeek 无损导入：按消息树完整重建，重新生成的备选回答与编辑历史产生的分叉全部保留，思维链、附件与联网搜索片段按原始数据保留
  • 合并模式保留本地内容，覆盖模式只定点替换对应导入会话

备份与迁移

  • 本机设置（窗口大小位置、桌面快捷键、聊天字号）可选择随备份流转，按设备识别恢复
  • 本地备份处理提示在导入导出时显示，任务结束自动退出
  • 备份页可查看和清理已记录的设备

助手与供应商增强

  • 助手接入业务数据库，支持分组、批量选择、移动、删除、拖拽整理
  • DeepSeek 默认 Anthropic-compatible 通道与专项适配（余额与模型列表自动改道到 OpenAI 兼容端点）
  • 头像裁剪、旋转、水平/垂直翻转，导出时保留变换

桌面与平台能力

  • 宽屏聊天区域拉宽开关（默认关闭）
  • JO-AIClient 更新检测（按当前平台匹配可下载安装包）
  • 用户数据目录入口（桌面端备份与恢复、存储空间页面）
  • Android 自适应刷新率开关（Android 11+，默认关闭即锁定最高刷新率）
  • Linux 应用自绘标题栏（不依赖窗口管理器，Windows/macOS 仍用系统原生标题栏）

继承 继承自 Kelivo 的基础能力 当前基座：Kelivo 1.3.0

  • 多供应商支持：OpenAI、Google Gemini、Anthropic 等主流供应商，支持自定义请求头与请求体
  • 思考与推理控制：推理预算滑块、思考开关
  • 自定义助手与提示词变量
  • 多模态输入：图片、文本文档、PDF、Word；长文本自动转附件，图片自动压缩
  • Markdown 渲染：代码高亮、LaTeX 公式（含中文字体回退）、表格
  • 语音服务：系统语音与多家网络 TTS、可配置 ASR、朗读音频导出
  • MCP 支持：Model Context Protocol 工具与 OAuth 授权，内置 fetch 工具
  • 网络搜索：集成二十余家搜索服务，并支持部分供应商内置搜索
  • 设备本地工具：日历、屏幕使用时长（Android）、当前位置（Android）、健康数据摘要、提醒事项、天气等
  • 自动重试：可配置等待策略，界面显示倒计时
  • 对话体验：会话单独指定模型、长回复分段气泡、气泡样式自定义、会话批量操作
  • 记忆系统：记忆提取、管理、上下文注入与策略配置
  • 数据备份：本地数据库快照恢复点、WebDAV / S3 云备份
  • 持久化：SQLite / Drift 存储聊天、消息分支与结构化附件
  • 其他：二维码分享供应商配置、自定义字体、启动故障自救、账号登录（ChatGPT、Grok、Kimi Code、Claude 等）
  • 设置与调度：设置搜索、世界书定时生效、手机端 MCP 绑定工作区
02

与 Kelivo 的关系

JO-AIClient 是 Kelivo 的下游改版。这里说清楚改了什么、没改什么、以及哪些问题应该回到上游解决。

上游基座

当前基座为 Kelivo 1.3.0，JO-AIClient 与上游保持同步。

应用身份已独立化

应用名称、包名、安装器标识、数据目录、更新源、构建产物名均已独立。

  • 可与原版 Kelivo 并存安装
  • 双方不会读取彼此的运行时数据

致谢与版权

感谢 Kelivo 作者及贡献者的开源工作。原项目版权归原作者及贡献者所有。

JO-AIClient 按 GNU AGPL-3.0 发布。

明确不提供

  • iOS / macOS 不支持。README 明确建议这类用户使用 Kelivo。
  • HarmonyOS NEXT 不支持。建议使用 kelivo-ohos。
  • 赞助商栏目 未保留上游的赞助商栏目与推广位。
